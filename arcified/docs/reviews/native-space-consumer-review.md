## Findings

1. **Correct the feature lifecycle catalog before using it for member-level extraction.** The `browser_elements_` row has no explicit pre-window cleanup in either [feature-members.json](../research/native-space-consumers/feature-members.json) or [feature-members.md](../research/native-space-consumers/feature-members.md). Retained [browser_window_features.cc](../research/native-space-consumers/chromium/chrome/browser/ui/browser_window/internal/browser_window_features.cc), lines 1253 to 1254, obtains `BrowserElementsViews` through `browser_elements_->AsA<BrowserElementsViews>()` and calls `provider->TearDown()`. This alias-based lifecycle call is missed by direct member-call accounting. Record the conditional cleanup and preserve its position before animation/actor-border teardown. Also remove line 1153 from `pinned_toolbar_actions_` initialization sites: `pinned_toolbar_actions_ = nullptr` occurs inside `TearDownPreBrowserWindowDestruction`, not lazy construction. The actual borrowed-pointer acquisition is line 1041; lazy find-bar construction is line 1281. All 122 declarations remain accounted for, but the claim of complete, accurately staged cleanup/initialization accounting needs these corrections. They do not block an extraction that preserves the whole existing feature teardown hook and its order.

2. **Correct E16's dialog and owner interpretation before implementing that consumer.** Its cited [devtools_window.cc](../research/native-space-consumers/chromium/chrome/browser/devtools/devtools_window.cc), lines 1971 to 2006, implements `ShowCertificateViewer`, not a connection dialog. Lines 1991 to 1992 select the inspected page when docked and `main_web_contents_`, the DevTools frontend, when undocked. The subsequent native-parent lookup therefore does not always follow the inspected page's Browser. Preserve this distinction when replacing the combined Browser/window lookup; unconditionally using the inspected page's presentation could move an undocked tools dialog to the wrong host. The broader conclusion that DevTools container/native-parent assumptions need extraction remains grounded. This correction affects E16's later implementation, not the first destruction patch.

3. **Correct E17's insertion coordinate.** [session_service_browser_helper.cc](../research/native-space-consumers/chromium/chrome/browser/ui/sessions/session_service_browser_helper.cc), lines 142 to 147, belongs to replacement handling. Actual insertion assigns the window ID at lines 92 to 101. Both paths support the need to preserve Profile-local session associations. Cite insertion and replacement separately so later transfer/session work does not audit only one of them. This is a citation correction, not a defect in the proposed session ownership split.

No source-backed architecture blocker was found for using the inventory to plan the first bounded extraction. The findings prevent calling the current lifecycle map exact or this review clean without qualification. They do not establish a need to solve multi-Profile hosting before making a behavior-preserving ordinary-window refactor.

## Ownership assessment

The lifetime interpretation is grounded in actual production code. [Browser construction/destruction](../research/native-space-consumers/chromium/chrome/browser/ui/browser.cc), lines 233 to 335 and 349 to 392, couples Profile-bound tabs/features/session records, a BROWSER process keepalive, a regular-Profile keepalive and physical window ownership. `Browser::Create` registers with the Profile manager only after construction returns. The callback creation overload posts completion after synchronous creation; it does not create a windowless context. The test-only custom-window check remains a real production boundary.

[BrowserWidget](../research/native-space-consumers/chromium/chrome/browser/ui/views/frame/browser_widget.cc), lines 113 to 142, first marks itself closed, synchronously closes owned widgets, then invokes feature pre-window teardown while widget state and BrowserView are still available. BrowserView remains the widget delegate. Lines 394 to 406 clear the native-widget pointer, obtain the Browser from BrowserView, force the existing close path, call the native base callback, and synchronously request manager destruction. This is direct Browser-specific lifetime authority in the widget, not merely theme or view coupling.

[BrowserManagerService](../research/native-space-consumers/chromium/chrome/browser/ui/browser_manager_service.cc), lines 32 to 55 and 81 to 177, is an owner with activation/close subscriptions, not a pointer registry. It extracts entries before destruction to tolerate reentry. Its header declares Browser ownership after subscriptions so the subscriptions survive Browser destruction. Its exact-context factory does not normalize OTR to the original Profile. Primary-OTR cleanup, printing-preview destruction and application-exit notification impose additional lifetime duties. A new process-owned host cannot inherit those duties merely by pointing several contexts at one native handle.

[UnloadController](../research/native-space-consumers/chromium/chrome/browser/ui/unload_controller.cc), lines 141 to 188, guards repeat `OnWindowClosing` after deletion is scheduled. Lines 942 to 983 mark completion, notify close observers, assess application shutdown and post deletion through a weak Browser pointer. Native-widget destruction separately requests synchronous manager deletion. The pending task then relies on invalidation to become harmless. Browser's own destructor also enters forced closing when needed, and manager `Shutdown` destroys owned entries directly. Thus the first patch must cover owner-initiated destruction as well as the widget callback and the posted completion path. The phrase "two deletion paths" identifies the normal posted/native-synchronous interaction; E03/E05 and Browser's destructor show why it is not an exhaustive list of destruction initiators.

The empty-strip distinction is also correct. Browser calls window close; UnloadController separately marks close-attempt state to prevent new tabs. Changing only Browser's callback leaves that second effect. The downstream last-tab flag inserts a replacement tab during close handling and supplies no host-lifetime solution. Existing force-skip shutdown behavior is a source observation, not approval for a new destructive policy.

Keepalive, session, lookup and dispatch classifications follow the source. Process BROWSER liveness and regular-Profile retention are different resources, with special OTR release and deferred Profile keepalive removal. Session helpers capture an exact Profile, tab model and session ID; Ozone metadata also encodes a window identity. Restore creates production windows per record, and the sync delegate CHECKs a window and reports `HasWindow()` true. A future host/session join must change those meanings explicitly.

Native-window lookup returns the first matching Browser, whereas tab lookup follows TabInterface ownership and checks collection membership. MRU, counts and physical activation also consume the combined owner. Toolbar/command/file-selection code captures Profile services and owners; changing the selected Profile getter cannot update those references. Theme/native-property readers, permissions, focus, accessibility, capture and native menus independently justify presentation authority. Retaining context observers therefore cannot grant inactive chrome input or popup authority. The catalog's owner codes remain proposed responsibilities, not verified safe placements for each unchanged feature implementation.

Exact-page transfer is a separate later proof. The retained detach/insert path can preserve a TabModel; the WebContents-only extraction destroys its wrapper. Same-Profile drag compatibility, delegate changes, modal cleanup, split references, empty-strip callbacks and failure ownership still need reconciliation. Neither retained unique ownership nor a successful insertion call proves document continuity, rollback or live transfer between the eventual hosts.

## First patch and remaining gates

The recommended first patch can stand independently as a behavior-preserving extraction of Browser-specific destruction authority. It has a concrete source dependency to remove and ordinary-window behavior to preserve. It need not create a multi-Profile host, make Browser windowless, replace BrowserView as delegate, change last-tab behavior or settle user close policy to be useful.

1. Establish the production lifetime owner's notification and invalidation route during construction. BrowserManagerService registration happens after Browser construction, so moving callbacks into `DeleteBrowser` alone would miss construction-time and direct shutdown/destructor paths. Do not merely relocate the `browser_view_->browser()` lookup behind a forwarding wrapper.
2. Preserve each path's existing order. In the widget destructor, owned widget closure precedes feature pre-window teardown while widget/views remain valid. In native destruction, close handling precedes the native base callback, which precedes synchronous manager deletion. Preserve manager removal/subscription lifetime and Browser/window/features/session cleanup and keepalive release in their existing positions. Preserve forced legacy native-loss behavior on ordinary windows without applying it as the future shared-host recovery policy.
3. Prove exactly-once completion under native destruction, already-posted deletion, reentrant observers, direct manager shutdown and partial construction. No duplicate session close, stale lookup, tab insertion into a completed Browser or early Profile release may result. These are acceptance conditions for the future patch, not checks executed by this review.
4. Locate actual coverage and GN targets in the separately authorized pinned prepared tree. The retained frame listing contains the named browser-widget, browser-view and focus-interactive test files. Their bodies and build targets were not reviewed here. The names alone prove neither existing coverage nor a passing test.

There is no inventory-based blocker to beginning that bounded patch design after accounting for these findings. Applying or accepting it still requires the prepared-tree source and focused native lifecycle evidence, which are outside this review. Preserving the entire existing pre-window hook keeps finding 1 from becoming a reason to omit individual cleanup during this first slice.

Later gates remain **OPEN**: exhaustive affected-consumer and enabled-feature/internal/factory/reverse-caller closure; real host/context construction; continuous actual top-level identity with no hidden/replacement backing windows; command and storage isolation; shared-Profile services and independent Space themes; empty/failure behavior; exact-object/document handoff and recovery; persistence/session joins; and installed Linux, Windows and macOS acceptance. The captured platform paths are targeted source samples, not complete Linux backend, Windows shell/UIA or macOS app-shim/menu/accessibility audits. The inventory explicitly records these limits and does not pass the integration plan's exhaustive inventory or native-proof exit conditions.
