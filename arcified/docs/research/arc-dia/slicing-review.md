# Arc and Dia backlog slicing review

Reviewed 2026-10-23. This is a review of all 108 issue records in `backlog.json` and the complete `fork-baseline.md`. I compared every issue key, title, build statement, acceptance list, blocker list, readiness label, source family, and evidence note. I checked that each blocker names an existing issue and that the blocker graph has no cycles. No issues were created and no implementation was inspected or changed.

## Overall findings

- The records generally describe observable outcomes and often call for native smoke tests, restart behavior, accessibility, or failure recovery. They are still draft slices, not uniformly ready-to-file GitHub issues. Many acceptance lists combine a feature's happy path with persistence, platform parity, accessibility, security, migration, undo, and performance. Keep these as one issue only where they deliver one user-visible capability with one coherent native end-to-end scenario; split independent surfaces and decisions otherwise.
- Most issue records repeat the same generic evidence sentence. It correctly warns that static presence is not runtime proof, but does not say what evidence applies to that particular feature. Arc help/release-note sources establish documented intent, not current runtime details or cross-platform parity. The baseline likewise reports no native Arcified patches, builds, or runtime checks. Replace the boilerplate with the specific source and the proof required to close that issue.
- The baseline establishes that Arcified Lab is only an extension prototype for snapshots and explicit local single-page capture. It is not a native sidebar, live Space model, browser runtime, or Dia assistant. Its Bun tests and three-OS extension CI must not be accepted as completion evidence for native issues. Native implementation issues should name a pinned Chromium/Helium source, downstream patch integration, native build, and the affected browser interaction. The `native-*` records already distinguish extension evidence; carry that distinction into all affected feature and release issues.
- Cross-platform desktop scope is explicit, but `spaces` depends only on `native-linux`; `profiles` and most core behavior then inherit a Linux-only foundation. Treat the native build/run prerequisites as a three-platform foundation or make each feature's platform acceptance explicit and prove which platforms it covers. A single Linux dependency does not establish Windows or macOS readiness.
- No blocker references a missing key and no cycle exists. Several edges encode implementation order without a demonstrated technical dependency. Keep true data-model prerequisites, but avoid serializing discovery, independent workflows, and product decisions behind unrelated UI features. `runtime-reference` is unblocked, which is useful: it can settle behavior before implementation rather than after a long build chain.
- Fourteen issues are labeled as requiring owner decisions, but that label is inconsistent: `sync-contract` clearly gates remote writes, while `boost-code`, `live-folders`, `memory-decision`, `calendar`, `automation`, and release records each contain concrete product/service/security decisions in their acceptance criteria. Keep decision work explicit and identify the decision-maker and decision artifact in those records. Some records are decision-plus-implementation issues and should be split so implementation can have a stable contract.
- The requested Dia-informed performance direction is represented by `perf-*`, but Dia evidence is not a measured target. `perf-baseline` should define a reproducible native comparison method, reference workloads, exact Arc/Dia artifact and platform evidence, and comparable Helium baseline; targets or regression gates must come from measurement and owner agreement. Vendor claims or extension timings alone cannot establish browser performance.

## Findings by issue key

### Native foundation and core workspace

- `native-linux`, `native-windows`, `native-macos`: Each is a useful platform-specific build outcome, but each acceptance list bundles build provenance with a broad smoke suite. Keep the launchable native artifact as the close condition and make the required smoke scenarios concrete and reproducible. Do not make feature work depend on a Linux-only build while calling the product cross-platform. Signing belongs to release work, not a development build issue.
- `spaces`: Core model and native sidebar interaction are bundled. Acceptance spans CRUD, ordering, selected-tab ownership, restart, destructive disposition/undo, keyboard, pointer, and navigation. Define the live Space/tab lifecycle contract first and give this one end-to-end flow; move sidebar polish or broad input coverage to their focused issues. Its `native-linux` blocker is incomplete for the stated three-OS product.
- `profiles`: Isolation is verifiable, but the issue combines identity ownership, Space assignment, multi-window behavior, restart, and destructive profile deletion. State the native profile boundary and a cross-profile leak test with synthetic data. Arc and Dia sources do not prove equivalent semantics; verify behavior before adopting it. Depends on the Space-to-Profile relationship, which is valid if that contract is established in `spaces`.
- `temporary-tabs`: Good user workflow, but opening/duplicating/reopening, all navigation controls, middle/modifier clicks, window switching, forms, media, and downloads are a broad regression matrix. Split tab lifecycle from input gesture coverage if they can ship independently. Add explicit native browser scenario(s); extension tests cannot prove this.
- `pins`: The durable item plus saved URL/reset contract is coherent, but the fourth acceptance item combines unresolved outbound navigation, preserving the prior page, reset-all, and collapse/expand controls. Runtime evidence is a prerequisite to settling navigation semantics, so this issue is not ready as labeled. Separate reset/navigation behavior from section-wide controls if independent.
- `favorites`: Cross-Space/Profile favorites are a distinct feature, but it duplicates much of `pins` lifecycle and placement while also specifying capacity. Reuse the pin contract and decide whether Favorites are the same persistent item type or a separate one. The capacity decision is correctly not inferred from Arc's documented limit; name its owner or leave capacity unspecified until a decision is made.
- `folders`: A reasonable organization capability, but hierarchy, move validation, Space moves, open-folder behavior, undo, restart, and bulk collapse/expand span model, interactions, and persistence. Define the hierarchy/move contract and a representative nested move/restore flow. “Without assuming a nesting limit” is not an acceptance result; avoid implementing an unbounded structure absent a product need.
- `multi-select`: Bulk actions across folder items, splits, mixed pin states, input conventions, assistive technology, drag preview, close protection, and undo are too much for one small issue. First define selection semantics and the smallest end-to-end operation; split bulk move, close, and split if independently usable. Blocking on all `folders` work is stronger than necessary for selecting a flat set of tabs.
- `archive`: Manual close/archive and restore have a verifiable lifecycle, but this combines search, cross-Space restore, permanent deletion, history distinction, and edge cases. Define what enters archive versus history and test close/restore plus permanent deletion. The `temporary-tabs` prerequisite is appropriate.
- `auto-archive`: A settings/product decision and an automatic data lifecycle in one issue. Split the owner-approved policy (eligibility, interval, exclusions) from implementation if the policy is not already settled. Interval is correctly not invented. `archive` and `pins` are real dependencies; verify downloads, forms, capture, and audible-state protection in native flows.
- `session-durability`: Important but large: schema validation, interrupted writes, crash recovery, folders, pins, splits, selected identity, and recovery reporting. Make the durable workspace schema and atomic recovery behavior a foundational slice, then add feature-specific persistence as each model lands. `folders` need not necessarily block the generic persistence foundation; clarify whether the dependency means folder schema or full folder UI.
- `undo-windows`: A clear closed-window restore outcome, but split/tab restoration, private-window exclusion, shared persistent objects, crash recovery, and session restore are separate lifecycle contracts. Keep closed-window undo separate from crash recovery as the text already says; specify one native reopen scenario and its ownership semantics.
- `tab-status`: Status indicators and four actions plus hidden/folder/Space states are a coherent sidebar capability, though visible indicators and control actions could be separate if needed. Define native status source and prove that the action affects the intended live tab, including when it is hidden.
- `window-ownership`: This combines the foundational model decision (move, mirror, or duplicate), tear-off, cross-window moves, shared visibility, failure rollback, profile isolation, restore, and concurrent edits. Decide whether the unit is tab ownership or Space ownership, then use one consistent ownership model and test it end-to-end. Do not gate basic work on full `session-durability` unless the chosen ownership contract actually requires it.
- `folder-preview`: Focused and testable, with a useful distinction between a projected active child and changing folder expansion. Cover pointer and keyboard in the same native scenario; nested-folder behavior depends on the actual supported folder model.
- `tab-handoff`: Depends on `window-ownership` and `favorites`, but “persistent tab” includes pinned tabs and Favorites. Define which item types hand off and whether the live page moves or is recreated. Its key observable outcome is preservation of the existing renderer state without duplicate live instances.
- `private-browsing`: Valuable security boundary, but it spans workspace persistence, captures, history, sync, AI, pins, shares, and profile behavior. Make the core private-window persistence contract one issue and require each optional feature to consume it; avoid making this single issue wait for all of `library` UI. Validate with app-owned persisted state and synthetic private content.

### Data, navigation, shell, and platform behavior

- `export`: A portable format and recoverable import flow are coupled but independently useful. Separate export from import/merge if they can ship separately. `session-durability` is relevant to the source schema, but does not have to block documenting or prototyping a format. Name fields and excluded data precisely.
- `arc-import`: This depends on `export`, yet importing Arc's format does not technically require a user-facing Arcified export feature. Share a stable internal schema/preview/validation layer rather than a delivery-order blocker. Owner-authorized fixtures and supported export versions are appropriate; do not claim undocumented format coverage.
- `browser-import`: Import from installed browsers is independent from Arcified export. Remove `export` as a prerequisite unless a shared importer contract is the actual dependency. Credential-store consent, category preview, cancellation, and locked-source recovery create a solid end-to-end result; name supported source browsers/OSes before filing.
- `prototype-migration`: Extension snapshot migration also need not wait for the user-facing `export` issue. It can consume the documented native import format. Keep the scope to URL/name/order/timestamp mapping and preserve the original storage as stated; extension prototype limits are not product capacity requirements.
- `command-bar`: A strong single entry point, but URL/search/tab-switch/command dispatch, side effects, private behavior, and abandoned-query focus all need distinct result semantics. Start with navigation and a small set of native commands or separate providers/actions. Verify actual address-bar focus and selected Space behavior in native chrome.
- `command-ranking`: Search across tabs, pins, folders, archive, and history combines several data sources and ranking. The repeatable corpus and latency observation are testable; avoid making history/archive/folders all prerequisites for a first cross-Space open-tab search. Build incrementally by source.
- `site-search`: Good independent command-bar extension. It need not block on all command-bar work if the input/result seam is defined; otherwise one command-bar path is a valid prerequisite. Include provider-name preview and a local test search engine, not production network assumptions.
- `tab-switcher`: A focused keyboard outcome; verify ordering, preview, release/cancel behavior, focus restoration, and profile/private isolation. `temporary-tabs` is a sensible model prerequisite, though the switcher may be prototyped against native tabs before the full Arc-style temporary-tab UI.
- `find`: Native find-in-page already exists in Chromium; define whether this is a shell integration/restyle or new behavior. Selection/focus preservation is verifiable, but `temporary-tabs` is not a necessary dependency if it only targets the active native page.
- `peek`: Preview-and-promote/dismiss is a clear interaction, but pin-reset behavior is not obviously required to preview a link. Remove `pins` as a blocker unless Peek specifically creates or promotes pinned items. Verify destination URL, history, opener, and keyboard/pointer behavior from runtime reference evidence.
- `little-arc`: A small window mode is distinct from tab ownership, but relies on platform window creation and transfer semantics. `window-ownership` is defensible only for moving/reusing an existing tab; otherwise split window appearance from ownership. Check native window controls on all OSes.
- `air-traffic`: Routing rules need an owner-defined matching precedence, default, and handling for ambiguous/conflicting rules. Current dependency on `little-arc` seems false if routing only selects a Space/Profile in the main window. Keep destination preview and normal browser URL validation as the close scenario.
- `sidebar-layout`: Resize/hide/reveal and focus are coherent, but measure platform-specific edge/reveal behavior and keyboard access. It should not depend on the full `spaces` feature if it can exercise Helium's existing sidebar independently; do depend on the native shell capability actually used.
- `split-horizontal`: A useful focused native split flow, but specify whether it is a transient arrangement or persisted model and how focus/navigation work. Use live native pages; extension side panels do not verify it.
- `split-vertical`: This is a layout variant plus persistence of a saved split. If the horizontal split already owns a general layout model, this can be a small extension; otherwise splitting orientation and saved-layout durability overstates the slice. `session-durability` is needed only for the persisted-layout portion.
- `focus-mode`: Depends on sidebar and split, but combining both may be unnecessary if focus mode only hides chrome. Define which controls remain available and retain keyboard escape; do not block on split if it can operate with one page.
- `space-themes`: Per-Space color/name/icon and restart are cohesive, but distinguish theme metadata from browser-wide themes and ensure contrast/accessibility criteria. The Space model dependency is valid.
- `motion`: This is broad polish across sidebar, Peek, and split, plus reduced-motion behavior. Make it a focused motion/accessibility issue for one interaction at a time or an umbrella that links specific implementation issues; avoid blocking all motion on three unrelated feature completions.
- `shortcut-settings`: Discovery/customization is a focused capability. `command-bar` is not a prerequisite for configuring existing browser shortcuts. Verify rebinding, conflict feedback, reset, and platform-specific defaults with native key events.
- `accessibility`: A broad audit of Spaces/sidebar, but depends on `folders` and `sidebar-layout`, which blocks accessibility work on the foundational controls. Accessibility semantics should be accepted with each control; retain this issue for an end-to-end audit across shipped native surfaces, not as a prerequisite to making any surface accessible.
- `ime-localization`: IME, bidirectional text, localization, focus, and all chrome are broad concerns. `space-themes` is an unrelated dependency. Test editable native chrome with representative composition and bidi input; scope this as a platform integration issue or split localization from input-method correctness.
- `window-chrome`: Useful platform-specific outcome, but caption controls, mixed-DPI displays, dragging/resizing, maximize/fullscreen/restore, and native menu behavior form a wide platform matrix. Do not require all three native builds as blocker references when each platform can proceed independently; ensure each acceptance result is from its native OS.
- `settings`: Search, reset, scope rules, many unrelated settings, restart, accessibility, and error cases make a very broad issue. Start with settings navigation/search and make each setting owner issue-specific. `profiles` is valid for per-Profile scope; `command-bar` is not necessary for settings deep links if direct navigation can be added separately.
- `onboarding`: Combines Profile/Space creation, browser import, default registration, AI choice, education, and progress recovery. Keep first-run path to usable local browsing as the end-to-end result; make import/default-browser/AI steps optional integrations with their own outcomes. The `settings` blocker should not prevent a minimal onboarding path if a later settings entry can be added in a follow-up.
- `compatibility`: This is a cross-platform verification matrix for web apps, extensions, passwords/passkeys, print/download, notifications, protocols, casting, PiP, and Widevine. It is too broad for one small issue and duplicates `site-controls`/`window-chrome` prerequisites. Split by native workflow or make it an explicitly non-blocking release test matrix with recorded OS results. Never represent extension CI as this evidence.
- `share-quote`: Copy URL/Markdown/selection and clean-link behavior are separate actions with different privacy semantics. Split or make the accepted formats precise; `site-controls` is not a technical prerequisite. Verify clipboard and private-page behavior in the native app.
- `automation`: The API/product decision and cross-platform adapter implementation are combined. Decide supported command surface, transport, and authorization boundary first. One end-to-end automation per OS is not a small first issue; start with a single safe operation and document platform limitations. `window-ownership` is needed only for operations involving ownership; command bar is not required for an automation API.

### Library and optional creation/sharing features

- `library`: A unified Library spanning saved material is broad. `archive` is one source but not required to establish a Library container for another item. Define the initial item type and one save/open/restore path, then add sections.
- `downloads`: Manage/progress/recovery is testable, but a native download manager may already exist. State the precise Arcified gap. It should not depend on the whole Library if it can be verified through the existing downloads shelf/manager.
- `recent-files`: Recent downloads and captures plus drag-out are two source types and platform-specific file operations. Split source support if independently shippable. Specify destination behavior and test native drag-out on each supported platform.
- `capture`: Page capture and region capture are distinct capture mechanisms, plus Library reuse and split-pane targeting. Split full-page/region capture from organization if needed. `split-horizontal` should not block single-page capture; native page capture must report unsupported/cross-origin behavior rather than silently omit content.
- `pip`: Picture-in-picture placement/return and Profile/window ownership are testable, but the browser may already provide native PiP. State the shell-specific improvement and verify return to the correct tab/window on each OS. `tab-status` may inform visibility but need not block core native PiP.
- `media-controls`: Focused controls for background audio. Verify state updates against native media sessions, including navigation and multiple Profiles; do not make the entire `tab-status` sidebar feature a prerequisite if the OS/browser media-session API is sufficient.
- `site-controls`: Site permissions and extensions are different control surfaces with security implications. Separate them, state which existing Chromium UI is being replaced, and verify permission changes affect only the intended origin/Profile. Split view/sidebar layout are not inherent prerequisites.
- `developer-mode`: Developer tools entry is a narrow shell integration. `site-controls` is not a necessary dependency unless the intended menu is part of that issue. Test attach/detach to the correct active page and preserve Chromium's security controls.
- `boost-style`: Visual CSS customization can be scoped and reset; define whether Boost is per Profile, site, or both. Keep this independent of general site permission chrome unless permissions are the chosen user-facing entry.
- `boost-zap`: A reversible element picker is a discrete interaction on top of visual Boosts. `boost-style` is a real dependency if it supplies persistence/reset; define how selectors survive site changes and what happens to hidden interactive controls.
- `boost-code`: Correctly recognizes executable customization as a separate high-risk decision, but the readiness label says ready while the acceptance requires inspection/confirmation and security-boundary decisions. Mark it decision-gated; decide whether authored scripts are in product scope before implementation. Do not let imported code execute on preview.
- `easel`: Local board, capture/link/text items, export, and offline editability are broad. Start with a local board and one item type; add capture and visual export as separate slices. Export of workspace data is not necessarily a prerequisite for local board editing.
- `live-capture`: Dynamic web-region refresh requires account/site permission, selector stability, refresh policy, and stale/error behavior not represented in acceptance. Clarify whether it is a local user-authored capture or a service integration. It properly depends on the board; add a user-visible refresh/disconnect scenario.
- `notes`: Import/export of historical Notes is separate from building new notes. Define the supported source fixture and mapping; `library` and `session-durability` are relevant to native storage, but do not let an unbuilt Library UI block an import-format decision.
- `share-folders`: Sharing link sets and local splits has distinct content/privacy rules and depends on a hosted or recipient transfer mechanism that is not specified. Split local export from service sharing; define included/excluded URLs and snapshot semantics. The dependency on `export` is sensible only if the same portable format is used.
- `live-folders`: One named GitHub-style workflow can be an end-to-end slice, but “such as” leaves provider and query behavior undecided. Keep its decision readiness, identify the owner and provider, and separate credential/service choice from folder UI. It does not need full Profile UI to test account scoping if a clear profile boundary exists.
- `easel-drawing`: Drawing, alignment, multiple content types, undo, accessible alternatives, visual export, source attribution, and scaling are too many independent board capabilities. Split drawing and export, and define the initial board item model.
- `shared-board`: Combines service decision, publishing, viewing, and revocation. Keep service ownership/access/retention/abuse decisions as a gate before implementation, then one end-to-end publish/view/revoke slice. A sharing service cannot be safely inferred from Arc documentation.
- `boost-sharing`: Preview/import/export is a coherent artifact workflow, but acceptance spans site scope, unsupported rules, gallery/hosting and reset after site change. Keep local portable exchange separate from any hosted gallery. The `boost-zap` dependency is not required to share ordinary visual styles if they are separate representations.
- `calendar`: Explicit account/provider decision, event visibility, timezone correctness, notifications, fallback, and multiple accounts make this a service integration rather than a small UI issue. Decide provider and account scope first; preserve Favorite fallback. The `profiles` dependency is meaningful for account isolation.

### Assistant and Dia-informed behavior

- `local-assistant`: The current extension sends a user-requested active-page capture to a local LM Studio endpoint, but baseline evidence says it is not a multi-tab assistant. The native issue must specify supported local provider/endpoint, context consent, cancellation, and one native request flow. `site-controls` is not a prerequisite unless it owns AI permissions.
- `context-selector`: `@tab` and `@space` selection is a good explicit user outcome. Separate selection preview from provider dispatch if that makes the boundary easier to verify. Profile isolation is a real constraint; test payload contents and ensure no unselected/private page is sent.
- `remote-provider`: Correctly follows explicit context and consent, but the provider, credentials, retention, and failure behavior are policy choices. Readiness should be decision-gated before enabling a provider; do not treat local LM Studio support as authorization for remote API transmission.
- `streaming`: Streaming/cancel/retry is a coherent interaction; specify partial-answer behavior on cancellation and ensure rendering does not block browsing. It can be tested independently of full local-assistant capabilities using a deterministic provider stub, so `local-assistant` need not be a hard blocker for UI work.
- `citations`: Exact source attribution is testable, but citation correctness is coupled to context identity and answer claims. Define the citation representation and a deterministic fixture; `streaming` is not inherently required if citations are generated on completion.
- `page-reading`: Scope is currently underspecified: “supported page content outside the browser UI path” could mean readability extraction, accessibility tree, or alternate capture. Name supported content and permission boundary. `context-selector` may be needed for selection, but a single-page reader can be prototyped without it.
- `ask-page`: Combines a local find action, page reading, citation, and assistant dispatch. Define whether it asks about selection or whole page and keep the explicit user action. The dependency chain is valid only if each prerequisite already exposes a stable callable contract; otherwise it blocks an integrated prototype unnecessarily.
- `link-summaries`: One explicit summary request is verifiable; requiring a remote provider couples a local/remote capability choice to content UX. Clarify supported provider and link-fetch boundary, including redirects/authenticated pages, before issue readiness.
- `tidy-titles`: Suggested titles are discrete; define preview/undo, source context, and whether the model can alter persistent pin labels. `pins` is relevant only to applying the title to a pin; preview can be implemented independently.
- `tidy-downloads`: Suggestions before rename are a clear safety boundary, but `downloads` UI is not necessary if the native download item API is available. Test that the original filename survives cancellation/failure and a user confirms the final rename.
- `tidy-tabs`: Suggested groups plus apply/undo are a sizeable model-assisted workflow. Define grouping input and allowed moves; do not require full `folders` if the result is a flat group. Ensure preview is not an implicit write.
- `chat-command`: A command-bar question is one integrated action, but `command-bar` and `local-assistant` need only expose a common input seam; their full feature sets need not both be complete. Keep explicit send/cancel and context disclosure.
- `skills`: Saving and running prompt workflows is broad and introduces a new format/trust model. Define a local inspectable skill schema and run one read-only workflow first; external effects belong under `write-tools` approval.
- `read-tools`: Activity UI duplicates source disclosure in context selection and citations. State the actual tools and events to be shown and test the log against emitted accesses; avoid waiting for all of `skills` if basic page-read tools exist.
- `write-tools`: Preview and approve external effects is a security boundary, not merely a UI feature. Define action taxonomy, cancellation, and failure/rollback semantics. A `read-tools` UI is not a technical prerequisite for safe approval.
- `ai-boundary`: Important threat model, but acceptance should name attacker-controlled page instructions and observable blocked effects. It is cross-cutting and should inform each assistant issue, not block all boundary tests until `read-tools` ships.
- `chat-history`: Local persistence, export, and deletion of assistant conversations/artifacts are multiple data lifecycle outcomes. Start with local history and deletion; export can share the workspace format only if explicitly designed to. Verify private context exclusion and Profile separation.
- `memory-decision`: Explicitly product-gated and correctly notes conflicting Dia evidence, but readiness says decisions are required. Keep inspect/edit/delete controls conditional on the owner's opt-in decision; do not treat a vendor changelog as proof of current behavior.
- `instant-links`: It is labeled as an evaluation, not a feature issue, and requires a synthetic comparison and scope decision. Keep as research/decision work until evidence supports a feature; do not create an implementation issue from the historical Arc Max name alone.

### Performance, recovery, sync, and release

- `perf-baseline`: This is a benchmark-plan issue across startup, restore, Space switch, rendering, memory, tab scaling, and assistant work on three OSes. Keep the end result as a reproducible baseline report with hardware/workload/source identity and measured distributions. Arc/Dia vendor statements are not numerical targets. Split assistant capture/streaming measurement if it can be done independently. The baseline itself should not require all feature flows to exist; a Helium reference workload can be recorded earlier.
- `perf-activation`: “Present the next tab before doing close cleanup” is an implementation strategy mixed with a perceived-speed outcome. Define the observable activation/close scenario and measure it against `perf-baseline`; preserve cancellation/yield behavior where cleanup runs asynchronously.
- `perf-startup`: Early usable-window restore and background tab loading are a coherent startup scenario, but distinguish launch-to-window, selected-tab usability, and full restore. `session-durability` is a data prerequisite, while a fully completed durability feature need not block benchmark design.
- `perf-discard`: Tab sleeping and restoring safely combines eligibility policy, memory effect, and wake-up correctness. Owner decisions are needed for eligibility; protect audio, forms, downloads, capture, and active work. `tab-status` is not necessarily required to implement the discard policy.
- `perf-profiles`: Unloading inactive Profile resources and isolation are distinct. Define lifecycle/resource measurements and prove no Profile identity leak; `profiles` is a valid architectural dependency.
- `bfcache`: Browser back/forward cache is an engine capability with Chromium constraints. Measure eligible-page retention and correctness rather than claiming every page is preserved. Split eligibility/diagnostics from UI if acceptance requires different mechanisms.
- `perf-hidden`: Hidden sidebar and split work is two surfaces. Choose one measurable redundant-work source per issue; `folders` is not required to measure hidden sidebar work.
- `perf-layout`: Anchoring content during sidebar and split transitions covers two independent layout paths. Separate them unless they share one native layout transaction and one benchmark.
- `perf-leaks`: Repeated workflows across Peek and split are a broad soak matrix. Make a focused resource ownership test for one workflow, define what resource is measured, and compare repeated runs to baseline; avoid treating noisy memory readings as proof without a method.
- `perf-energy`: “Keep idle browsing quiet” lacks a defined workload and observable result. Establish a reproducible idle scenario and report CPU/wakeups/energy proxy per OS; do not introduce a threshold absent measured baseline and owner decision.
- `perf-ai`: Assistant startup, rendering, and responsiveness during browsing combine provider latency and native shell responsiveness. Separate model/network latency from browser-owned work; test with deterministic delayed responses and cancellation. `page-reading` is not required to measure assistant UI rendering.
- `crashed-tab`: Recovery UI and durable workspace recovery are distinct. Define renderer crash detection/retry and verify session identity, while `session-durability` governs persisted workspace state. Do not promise renderer memory restoration.
- `sync-contract`: Owner decision and encrypted proof-of-concept are combined. Split the scope/security decision from a controlled local/service round trip after service ownership and key model are approved. `export` can inform data shape but should not block a threat-model decision; Profile semantics may be a required schema boundary.
- `sync-enroll`: Device identity/enrollment and UI state are an integration slice. It is correctly gated on an approved `sync-contract`; specify a synthetic account and no-readable-data result for rejected enrollment.
- `sync-conflicts`: Merge semantics are difficult and current acceptance is broad across all object edits, deletes, clock skew, tombstones, and local recovery. Start with one concurrent conflict class and deterministic state fixtures after a stable sync protocol exists. `sync-enroll` need not block pure merge-engine tests if protocol types are defined.
- `sync-recovery`: Correctly decision-gated, but combines recovery, revocation, key rotation, password change, key loss, interrupted operation, and service shutdown. Decide recovery/key model first, then test one recovery and one revocation flow. Avoid requiring a production service before synthetic tests.
- `release-linux`, `release-windows`, `release-macos`: Platform-specific package outcomes are appropriate, but each mixes identity/channel decision, signed/authenticated publishing, install/upgrade/uninstall/rollback, data durability, and credentials. Separate package build/install verification from public update service if independently deliverable. `session-durability` is a sound data-preservation prerequisite; specify the supported package and update mechanism per OS before filing. No signing credentials belong in issue text.
- `engine-updates`: The recurring maintenance outcome has no finite close condition as written. Frame it as a repeatable update procedure/CI gate for a pinned Chromium revision, with a concrete update change and patch/build evidence; do not use this evergreen issue as a blocker for all initial native builds. Verify current security information when executing, not as a static acceptance claim.
- `runtime-reference`: Useful, but it bundles many scenarios and both Arc and Dia, requiring screenshots/recordings across different platforms and potentially authenticated features. Keep as a research parent with child scenario records or split reference captures by coherent interaction. The issue should record exact app artifact/version/platform and distinguish observed behavior from inference. This is not implementation or feature completion.
- `retirements`: This is a large disposition inventory across many unrelated historical features, services, mobile scope, and Dia Memory. It is research/owner-decision work rather than one small implementation issue. Split into decision records by product area and cite evidence per claim. Keep unavailable vendor services and mobile-only features out of desktop parity claims.
- `release-ux-check`: A valid final verification matrix, but it depends on all three platform releases and spans every feature, accessibility, touch/keyboard/IME, restart, failure, and data-loss cases. Treat it as a release gate/checklist that links each per-feature test result; do not duplicate acceptance already owned by feature issues. It cannot close while any applicable platform/feature remains unknown, as the record says.

## Blocker review

The graph is acyclic and every blocker key resolves. The following are likely false or unnecessarily broad dependencies and should be removed or narrowed unless an implementation-specific reason is added:

- `spaces` -> `native-linux`: incomplete platform prerequisite; use the native foundation for all target OSes or explicitly state which platform-specific feature issue is being unblocked.
- `multi-select` -> `folders`: flat tab selection can precede nested folders.
- `arc-import`, `browser-import`, `prototype-migration` -> `export`: these imports can use a documented internal format without waiting for the user-facing export feature.
- `command-ranking` -> `archive` and `folders`: begin with open tabs; add result sources incrementally.
- `peek` -> `pins`: preview does not inherently require pins.
- `air-traffic` -> `little-arc`: routing can be useful without a lightweight window.
- `split-vertical` -> `session-durability`: only needed for saved splits, not vertical split interaction.
- `focus-mode` -> `split-horizontal`: a one-page focus mode is possible.
