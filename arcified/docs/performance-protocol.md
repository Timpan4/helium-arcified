# Browser performance protocol

Issue: [#20, reproducible performance baseline](https://github.com/Timpan4/helium-arcified/issues/20).
This is a protocol and synthetic fixture artifact. No comparative benchmark, native runtime result or performance target was measured here.

The [issue source](research/arc-dia/publication/perf-baseline.md), [Dia research](research/arc-dia/dia-ux-performance.md) and [YAB research](research/arc-dia/yab-inspiration.md) establish evidence limits. Vendor claims describe possible mechanisms, not numerical targets. YAB's WebKit/macOS comparison is not a Chromium baseline; Dia's release notes do not establish Linux behavior. Prioritize native UX, platforms and core performance. AI workloads are deferred. Cross-device sync is excluded.

## Evidence boundary and reuse

The [fixture directory](../performance/README.md) supplies public synthetic content served only on loopback, explicit workload configuration, page observations and recording templates. It is not a native instrumentation harness. Extension tests cannot prove native startup, chrome interaction, rendering or resource use.

Inspect the tested build's existing native diagnostics before adding instrumentation. This checkout's [patch series](../../patches/series) already names native tab search, vertical/compact layouts, MRU cycling, hibernation and session restore patches. In particular:

- [Memory-saving defaults](../../patches/helium/core/memory-saving-by-default.patch) enables the memory-saver preference. Do not assume a fresh profile means all tabs remain loaded.
- [Lazy session restore](../../patches/helium/core/lazy-session-restore.patch) defines visible/deferred load policies and restore trace events. Distinguish restored tab identity from a loaded renderer or painted page.
- [Tab-restore lifetime changes](../../patches/upstream-fixes/tab-restore-live-tabs.patch) are adjacent recovery code. Closed-window undo and whole-process restart are separate paths.

These are source observations, not proof of shipped behavior. Reuse native task/process mapping, tracing, lifecycle diagnostics, tab search and omnibox where the actual build exposes them. Record the exact entry point, tool version and settings after checking it. A missing native command surface is an unsupported scenario, not permission to time an HTML imitation or silently substitute an extension. Any implementation change belongs in a separate native task.

## Reference machine, builds and conditions

1. Designate a reference machine for each of Linux, Windows and macOS. Fill [run.template.json](../performance/run.template.json) before measuring. Record CPU model/topology, RAM, storage/filesystem, GPU/driver, OS/kernel, compositor/window system, display resolution/refresh/scale, input device, power source/policy, thermal condition and background activity. No reference hardware has been selected by this artifact. Do not pool platforms or machines into one distribution.
2. Identify the fork and matched Helium baseline by repository/base/Chromium revisions, dirty diff hash, binary hash, version, architecture, build mode, compiler, GN arguments, packaging and launch flags. Prefer matching the engine revision and build configuration. If matching builds are unavailable, label the comparison confounded and identify the differences; do not attribute an engine or debug/release difference to Arcified UI.
3. Match layout, bounds/display, language/fonts, animation/reduced-motion/accessibility settings, hardware acceleration, cache policies, restore policy, memory saver, discard exemptions, site isolation and policies. Record settings rather than assuming equal defaults. Separately label an optional product-default comparison, if requested.
4. Use dedicated synthetic profiles, no personal browsing data, no signed-in accounts and no sync. Record onboarding, update/component checks, telemetry, crash reporting and service state. Match extensions, blocker version and filter revision. A blocker-off isolation condition and a matched blocker-on condition answer different questions; choose and name the condition. Do not disable security protections to improve a score.
5. Keep fixture revision/content hashes, URL origin/port, server runtime/cache policy and workload manifest identical across the pair. Local HTTP removes external site variability but measures loopback and a server sharing this host. Record server CPU/I/O separately. For an optional public-site follow-up, explicitly approve the site list and network effects, pin content where permitted, and record date, route, DNS/TLS, connectivity, shaping, redirects, response hashes, failures and caches. Changing live public sites cannot establish a reproducible baseline by themselves.

## Session and cold/warm preparation

Use [session.template.json](../performance/session.template.json) as a recording contract. Fill its nulls, expand windows/tabs deliberately, and retain exact ordered URLs, tab identities, active selections, pins/groups, layout, synthetic form/scroll state and expected lifecycle state. Its object placeholders do not specify a session size. Choose the distinct session sizes needed to expose scaling, record the reason for each choice, and preserve actual counts with results. There is no tab-count cap.

The launcher form requires `id`, `rows`, `textRepeats`, `batchRows`, `requests` and `responseBytes`. Rows/text affect DOM and layout; batching affects responsiveness during construction; sequential requests/bytes affect local transfer and body consumption. These are workload variables, not equivalent memory-byte allocations or browser limits. Use the same choices on both builds. Deterministic unique titles provide native tab-search candidates. The state input, row numbers and scroll position make state loss detectable. The paired-document link enables normal navigation and history tests. The page does not force BFCache eligibility or eviction.

1. Seed each product's isolated profile from the same manifest, using that product's own profile format. Save the equivalent restore session through native UI. Verify identity, order, selection and groups/pins against the manifest. Never clone a live profile or rely on cross-version profile compatibility. Keep protected seeds unchanged and create disposable run copies.
2. For a process-cold launch, close only the test instance, confirm its entire process set exited, then start it with the prepared profile and exact recorded command. Trace before launch. An already-running instance can receive a launch request without starting a browser process; detect and classify this separately.
3. Label profile state independently: fresh-profile/onboarding, seeded restore, or reused profile. Fresh profile is not a substitute for the seeded restore condition.
4. Label storage/OS cache state independently: controlled cold with recorded preparation, warm with the exact priming action, or uncontrolled/unknown. A process restart does not clear OS page cache, GPU caches or profile caches. Do not flush host caches or reboot without explicit authorization. Where that preparation is unavailable, keep the cache axis unknown.
5. Label browser HTTP, code/GPU, DNS/TLS and connection state independently. `no-store` affects fixture HTTP caching; `revalidate` permits storage with validation. Neither creates all forms of cold/warm state. A warm interaction uses an explicitly recorded prior activation/navigation in the existing process; a warm-cache process launch is a different condition.
6. Record initially loaded, deferred, frozen and discarded tabs from available native diagnostics. If lazy restore loads only visible tabs, preserve that distinction instead of declaring all restored content ready. Repeat the manifest's activation sequence to observe deferred loads separately.

Owner inputs before a run: machine/build pair, session sizes/content, native actions and command queries, run count/repetition plan, paired run order, warmup procedure, sample cadence, observation windows, stop conditions and any operational quiescence interval. Record these choices and their rationale before collecting results. No value is supplied here for durations, run counts, latency budgets, timers or thresholds. If a choice remains unmade, that measurement remains unconfigured.

## Milestone contract

For every milestone retain scenario/run/action identity, event name, raw timestamp, units, clock domain, source artifact/event locator, method, uncertainty and observed/missing status. Use elapsed times only within a shared clock, or with a recorded clock mapping and its error. Page `performance.now()`, page time origin, OS monotonic clocks, Node monotonic timestamps and video frames are not interchangeable clocks.

| Milestone | Required observation and boundary |
| --- | --- |
| Launch request / process start | Record both the external launch action and OS creation of the actual browser process. Report which starts the startup metric. Process creation excludes launcher delay. |
| Input | Native OS input or trace event for the selected action, including target and device. A page event timestamp is delivery to the document, not hardware input time or native chrome dispatch. Label automation dispatch separately from trusted physical input. |
| First visible response / perceived response | First frame showing the intended selected tab, command results, window or scroll change, with correct identity. Use compositor/presentation trace or synchronized capture of the actual UI. Focus changes and DOM mutation alone do not prove visible response. Record capture frame resolution and occlusion. |
| Input-ready | A defined follow-up input is accepted and its correct result observed, separately for browser chrome and page. Record probe dispatch, handler and visible result. An enabled control, window existence or fixture-ready marker alone does not prove this. |
| Fixture-ready / content-ready | The fixture's `fixture-ready` means required rows exist and chosen response bodies were consumed. Record the native feature's distinct readiness contract. This marker can follow early echo input and can be delayed by background frame throttling. |
| Paint / presentation | Preserve navigation paint entries where supported, rendering trace and presentation evidence. First paint/FCP concern a document, not tab activation of existing content. `requestAnimationFrame` is a callback opportunity before rendering; neither it nor a double callback certifies pixels reached the display. |
| Network milestones | Preserve request start, headers/response-end, resource timing, body consumption and failures. Document load is not completion of later fetches; all chosen fixture bodies consumed is not browser-wide network completion. Include background/browser-service requests in a separate scope. |
| Quiescence | Operational absence of named pending/recurring work during an owner-defined observation interval, evidenced by tasks, network and counters. Declare scope, exclusions and observation interval first. Report non-quiescent or unassessed if the condition is not met or configured. No timer or network-idle heuristic silently supplies this milestone. |

Compute and label input-to-visible, input-to-handler and input-to-ready separately. For launch, report launch-to-window, chrome-ready, selected-content-ready and deferred-content activation separately. A missing timestamp is null with a reason, never zero. A paint, network or quiescence endpoint must not be relabeled perceived latency.

## Scenario coverage and direct checks

For each scenario, start external tracing/counter collection before the action, record the action and expected result, execute the manifest, preserve raw artifacts and stop at the chosen endpoint or cancellation. Use native chrome for native actions. Capture correctness as well as timing; failed actions do not count as fast successes.

| Scenario | Workload and action | Evidence, resource scope and likely competing limits to investigate |
| --- | --- | --- |
| Startup and restore | Process-cold and warm-cache launches of each chosen seeded session; separately test an existing-process window request. Verify active page, identity/order, controls and follow-up input. | OS process start, first presented window/chrome, native input-ready, active fixture-ready and deferred activation. Trace profile I/O, startup tasks, renderer creation, favicon/restore work and memory. A window can be usable while hidden tabs remain deferred. |
| Input-to-visible activation | Switch between manifest tabs by declared pointer/keyboard/MRU actions; close the selected tab and verify its successor. Include loaded, deferred and deliberately hibernated targets. Repeat with supported sidebar layouts/states. | Actual input, correct selected title/page, focus and echo result; native trace for UI scheduling, relayout, compositor and cleanup. Distinguish renderer loading from chrome delay. Check background cleanup contention rather than assuming it from vendor reports. |
| Navigation and history | Follow the paired-document link, navigate by native address entry, back/forward and reload. Set synthetic form/scroll state first. | Input/commit/paint/body-consumed/fixture-ready and state correctness. Record `pageshow.persisted` for an observed BFCache restoration and native diagnostics for miss/eviction reasons. A reload is a distinct non-history path; do not claim a forced BFCache miss from the fixture alone. Account retained renderers and cache work. |
| Native command search | Populate manifest titles, synthetic bookmarks/history only if used. Open the native surface, type exact query sequence, observe expected ranked results, select a target, then test Escape/focus return. | Separate opening, each query's input-to-result presentation, selection-to-activation and input readiness. Record candidate/query corpus, result correctness, local versus remote suggestions. Disable or isolate remote suggestions by recorded policy. If only Helium tab search/omnibox is available, report those scoped baselines; an unavailable Arcified command bar stays unavailable. |
| Scrolling | Ensure rows exceed the chosen viewport, using owner-selected size. Scroll page and native sidebar independently with the specified device, direction, distance, pace and layout. | Input trace, presented scroll displacement, frame intervals, dropped/missed presentations according to the instrument's definition, and final position. Record refresh/VRR, scale, compositor/main-thread work, layout and raster/GPU activity. A page scroll event counts delivery, not smoothness. |
| Memory and lifecycle | Sample before opening, after readiness, across the chosen activation sequence, after native hibernate/discard and after close. Return to each affected tab and inspect form/scroll and reload/restore state. | Whole-process-set and per-role memory over time, current versus peak, swap/compression and page faults. Record live/deferred/discarded renderers and BFCache residency. DOM row count is a workload choice, not a measured memory amount. Separate shared pages from private footprint and retention from a demonstrated leak. |
| Idle work | After a recorded readiness point, observe unchanged foreground, background, collapsed sidebar and occluded/minimized states separately, then reactivate and verify correctness. | CPU time deltas, wakeups/timers/tasks, network/I/O, process membership, GPU and optional energy/sleep eligibility over the chosen window. Attribute recurring browser, extension, server and OS work. No recurring fixture loop after readiness does not prove browser quiescence. Sleep assertions are platform-specific. |

The fixtures contain no media, downloads or service workers, and do not model real-site protection policies. If those become a later test requirement, add a separately approved public/synthetic fixture and label the expanded workload. Do not force resource pressure, inject crashes or suspend the host as an implicit part of this protocol.

## Process and resource accounting

1. Identify the test browser by executable identity, dedicated profile and root PID plus process start time. Capture child creation/exit throughout the run, including short-lived children. Record browser, renderer, GPU, network/utility, extension and crash-handler roles. PIDs can be reused; a final process snapshot alone loses transient costs. Shared browser-service processes require explicit attribution or a stated gap.
2. Keep renderer/task-to-tab mapping from native diagnostics. Tabs do not equal processes: site isolation, shared renderers, deferred tabs, BFCache and split views change the relationship. Report total test process set and role breakdown, not only the foreground renderer. Put server, capture tool and unrelated OS processes in separate accounting groups; also report host pressure that can confound the run.
3. Choose installed OS-native tools and record exact commands/options, permissions, counter semantics, clock, sample cadence and overhead. Suggested capability map below is a collection plan, not evidence that these tools ran or are available. Do not install global tooling or elevate silently. If a counter cannot be obtained, retain the gap rather than substitute a different metric under the same name.

| Platform | Collection candidates and caveats |
| --- | --- |
| Linux | `/proc` process identity/stat and I/O, `smaps_rollup` PSS/private/RSS where permitted, scheduler/perf tracing when available, compositor/GPU presentation diagnostics. Sum PSS as proportional shared attribution; summed RSS double-counts shared pages. Record swap, faults and permission gaps. |
| Windows | ETW/WPR/WPA when installed and authorized for process/thread/CPU/I/O/presentation; native process counters for private bytes, working set and CPU time. Working set is resident memory, private bytes is committed private memory. Preserve shared-process and sampling limitations. |
| macOS | Instruments or installed native process sampling, physical footprint/resident counters with their definitions, compositor presentation and native energy/sleep-assertion diagnostics. Compressed memory and physical footprint are not interchangeable with Linux RSS or Windows private bytes. Record tool permissions and availability. |

For CPU, retain cumulative CPU seconds and elapsed wall interval. CPU utilization needs an explicit denominator, per-core or whole-machine, and topology. Preserve sampling intervals and gaps. Report memory in stated byte units with current/peak method; do not sum per-process peaks from different times and call it a simultaneous peak. Do not add RSS, private memory and GPU memory into one total. Report GPU attribution uncertainty. For idle, retain CPU/I/O/network deltas, task/wakeup counts and the actual elapsed window. Energy requires a supported calibrated meter/counter and power conditions; CPU use alone is not energy or battery life.

## Raw evidence, comparison and cancellation

1. Preserve an immutable result bundle per run outside the repository: completed session/run records, exact launch and collection commands, settings/build identities, page JSON exports, server stdout, native traces, OS counters/process membership, capture files, errors and operator action log. Record content hashes and tool versions. Keep originals; derived tables link observation IDs and raw event locators. Public/synthetic data only.
2. Register the repetition/order plan before running. Pair fork and Helium under the same conditions. Use the owner-chosen alternating or randomized order and preserve the actual sequence to expose drift. Keep warmup runs identified and separate, with reasons. Record incomplete, failed, cancelled and invalid runs and any exclusion reason. Never silently retry or discard an outlier.
3. Plot or publish individual observations and distributions by scenario, build, platform and cache/lifecycle condition. State actual sample count, spread, missing observations and paired deltas. Choose estimators and uncertainty methods that the sample supports, document them, and retain underlying data. No default percentile or single score hides distinct endpoints or failure rates.
4. Explain every reported number: metric formula, unit, denominator, measured work, endpoint, clock resolution, observer overhead and limiter evidence. Use profiles/counters to identify the limiting code path/resource. Test competing explanations such as cached/skipped work, failed requests, deferred tabs, server contention, instrumentation, build mismatch, power/thermal drift and incomplete process accounting. If the limiter remains unknown, say so; the observation is provisional, not an optimization conclusion. Do not infer a cause solely from a source-code guess.
5. Keep cancellation available through fixture controls and collector stop controls. Stop only the test processes started for this run. Record the stop action/time/reason, completed work and missing milestones; finalize and preserve partial traces/counters where the tool supports it. A fixture response counts as completed when its body is drained and its length validated, before the post-body frame wait. Exports and cancellation retain that count and consumed bytes; cancelling the final frame wait does not establish readiness. Do not convert cancellation into a successful latency, timeout score or fabricated endpoint. The fixture can abort fetch/frame waits, but a synchronous chosen batch/allocation can delay the button; externally stopping the isolated test instance is a separate recorded abort action.
6. Choose targets only after measurements, limiting mechanisms, uncertainty and owner needs are available. This protocol supplies no speedup, memory budget, run duration, fixed quiet interval or vendor-derived cap.
