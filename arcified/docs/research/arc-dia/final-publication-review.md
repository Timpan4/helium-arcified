## Recommended later refinements, not publication blockers

1. Clarify decision closure in `skills`, `read-tools`, `write-tools` and `memory-decision`. Their decision kind and the catalog's `decisionVerification` correctly permit approval or deferral, but some build and acceptance wording still sounds like delivered behavior. Label those clauses as requirements for any accepted implementation. A recorded deferral must be able to close the decision without a native tool, service account or memory implementation.

2. Make later-feature integration ownership explicit when work begins. `undo-windows` names split restoration while depending only on `session-durability`; `site-controls` names Peek/splits before those dependencies; `workspace-operation-journal` names folder and Space operations before their full management flows. State which supported-object scenario closes the first slice and which later feature must add its integration check, or add the relevant completion dependency. `security-surfaces`, `split-persistence`, `credentials-flow` and the release matrix already provide useful follow-up locations. Do not create a global dependency cycle or postpone each feature's basic safety and accessibility.

3. Carry the authorization gate into feature enablement. For `local-assistant`, `remote-provider`, `page-reading`, `agent-workspace` and any later accepted tools, explicitly require the applicable `ai-boundary` cases before enabling the capability outside the development harness. Keep implementation prerequisites separate from that enablement condition so the validation issue can exercise the implementation. The contract and hostile-fixture requirements are present; this refinement makes their operational sequencing harder to misread.

4. Preserve readable evidence when rendering leaf issues. Artifact-backed keys such as `automation`, `pin-section-controls`, `blank-window`, `manual-cleanup`, `browser-diagnostics` and `split-actions` should link to the roadmap's pinned identities and a durable artifact summary, or include the relevant short observation. A mutable `Dia-latest.dmg` URL alone is not the inspected identity. Tailor generic platform/source wording on fork-only work such as `native-linux`, `prototype-migration` and `schema-migrations`; use precise dated sections for historical decision records. This is publication fidelity work for the parent, not a request for additional binary analysis.

5. Remove residual scope wording during issue grooming. `capture` still mentions a region although `region-capture` owns the picker; `easel-drawing` still says portable export although `board-export` owns it; `sync-recovery` still mentions revocation although `sync-revoke` owns it. Narrow those descriptions to the named outcomes and retain the cross-links. Likewise, make `hosted-sharing`'s revocation wording explicitly mean future service access, matching `board-sharing`, without promising deletion of recipient copies.
