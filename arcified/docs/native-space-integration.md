# Native Space integration

Status: preparatory design for [issue 32](https://github.com/Timpan4/helium-arcified/issues/32), 2026-10-23. No native implementation or acceptance is claimed.

The required UX needs a native window ownership refactor. Chromium `155.0.8059.79` explicitly binds each desktop browser window and all its tabs to one immutable Profile. Helium's vertical layout and split presentation retain that assumption. A sidebar adapter that changes `selected_space` or displays another Profile's WebContents in the existing BrowserView cannot establish correct command, service, session or window ownership. See [C1 and C2](native-space-source-references.md#c1-desktop-window-and-profile-ownership).

Investigate one real native window host with separate Profile-bound browsing contexts. Keep each page's actual TabModel, WebContents, navigation controller and BrowserContext intact. This is a recommended architecture investigation, not an available Chromium API or a demonstrated implementation. A heterogeneous Browser is the competing design. Neither is proven viable by the standalone model. The [independent design review](reviews/native-space-design-review.md) found no blocking architecture defect within its source-investigation scope; native feasibility remains unproven. The [design response](reviews/native-space-design-response.md) records this authority update and the next source-design gate.

## Authority and evidence

The owner has approved shared saved items, window-local temporary tabs, switching Spaces across Profiles in the same native window, and bringing an already-live saved page into the requesting window with its state preserved. Do not substitute another OS window, relabel a live Profile, reopen/clone current navigation, or use hidden backing OS windows to claim the requirement is met.

The later owner approvals, recorded in the [version 3 contract](lifecycle-contract.md#evidence-and-decision-ledger) and [policy response](reviews/lifecycle-policy-response.md), now govern integration:

| Approved choice | Required native behavior |
| --- | --- |
| Each Space chooses exactly one Profile; multiple Spaces may share it | Resolve actual Profile identity independently of Space identity. Sharing a Profile must share its real services, without merging Space presentation. |
| Sign-ins, site settings and Favorites are Profile-scoped | Spaces sharing a Profile expose the same Profile data. Distinct Profiles retain separate security/storage ownership. |
| Themes are Space-scoped | Apply presentation from the selected Space without changing a Profile preference for every Space sharing it. |
| Outbound links from saved pages open temporary branches | A browser-classified outbound link creates a local temporary in the source page's current window, Space and real Profile. Preserve the saved page, its destination, current navigation, identity and activity. |

## Test the ownership premise first

The hypothesis was that existing Browser/Profile/WebContents primitives could be bound to the model while retaining the current desktop window ownership contract. Source inspection falsifies that hypothesis for cross-Profile switching.

1. `BrowserWindowInterface::GetProfile()` promises a fixed Profile and same-Profile desktop tabs. `Browser` holds a const Profile pointer, one tab strip and one owned window. Its constructor creates the strip with that Profile. The custom-window injection parameter is test-only, enforced with `CHECK_IS_TEST`. Creating stock hidden Browsers is therefore not an established production host mechanism. [C1](native-space-source-references.md#c1-desktop-window-and-profile-ownership)
2. BrowserView holds a const browser pointer, observes its tab strip, constructs its toolbar and publishes BrowserView/Profile pointers on the native window. BrowserWidget uses BrowserView as widget delegate and synchronously destroys that browser when the native widget dies. Swapping a view or modifying a window property cannot repair this ownership chain. [C2](native-space-source-references.md#c2-view-widget-and-command-coupling)
3. Toolbar, location bar, command controller, shortcut service and theme code capture Profile-bound objects. A changing Profile getter would violate the interface contract and leave cached services and observers stale. Browser navigation also derives the initiating Profile from the source browser. [C2](native-space-source-references.md#c2-view-widget-and-command-coupling), [C4](native-space-source-references.md#c4-navigation-and-session-boundaries), [H1](native-space-source-references.md#h1-helium-patch-reuse-and-constraints)
4. `WebView::SetWebContents` supplies native view attachment. It does not establish Browser ownership, command routing or a security guarantee for mixed-Profile browser chrome. Split view likewise operates within a BrowserView and its tab strip/Profile. [C3](native-space-source-references.md#c3-live-identity-and-handoff), [H1](native-space-source-references.md#h1-helium-patch-reuse-and-constraints)

The finding is a required refactor, not proof that same-window multi-Profile UX is impossible. Before binding model IDs to production objects, prove a supported production ownership route that preserves the top-level OS window while presenting different real Profiles. Removing the drag Profile check, mutating `Browser::profile_`, returning a selected Profile from the old interface, or sharing an unmodified BrowserView does not satisfy that gate.

## Competing designs

| Design | Reuse and benefit | Cost and falsification condition | Judgment |
| --- | --- | --- | --- |
| A. Native host independent of Profile-bound browsing contexts | Keeps homogeneous native tab models, Profile services and page identity. The host owns OS lifetime and Space presentation; the selected context supplies Profile-bound chrome and commands. | Extract production construction/lifetime from Browser/BrowserView/BrowserWidget; replace native-window assumptions and restore grouping. Reject if the implementation needs a backing OS window, a changing legacy Profile getter or an unsafe service mismatch. | Preferred investigation. Greatest retention of existing security/service assumptions. |
| B. One heterogeneous Browser and tab strip | Unified window selection and one visible tab model. | Replace the desktop interface invariant and audit browser-wide Profile users, tab groups/splits, commands, helpers, shortcuts, dialogs, native properties and session persistence. Per-tab Profile access alone cannot fix window-scoped state. | Coherent alternative, broader security and maintenance surface. |
| C. Retain native widget, swap Profile-specific chrome trees | Could be a presentation variant of A; retained chrome might avoid rebuilding every Profile-bound control on a switch. | BrowserView's const owner, widget delegate, controller observations and destruction path still require explicit production refactoring. Every popup, accelerator and asynchronous callback must track its actual owner. | Evaluate only within A. It is not an existing reparenting API shortcut. |

A separate OS window per Profile fails the approved requirement. A single Profile with renamed Spaces or ad hoc storage partitions changes the required Profile semantics. Neither is a fallback implementation of this issue.

## Proposed ownership seam

These are responsibilities to extract, not declarations of new classes or guessed C++ signatures.

| Owner | Responsibility | Boundary |
| --- | --- | --- |
| Workspace coordinator | Durable Space/item identities, attachment graph, selected Space, presentation order, command serialization and reconciliation | Never owns a navigation controller or credentials. Do not install it under one selected Profile's lifetime if it coordinates others. |
| Native window host | Actual OS window, native lifetime, frame, window-level focus, attachment presentation and selection publication | `WindowId` identifies this host. It must survive switching Profiles and an emptied browsing context. It does not implement a changing `GetProfile()` on the legacy browser interface. |
| Profile-bound browsing context | Real Profile lifetime, homogeneous tab containers, Profile services and context-bound chrome | Distinct from `content::BrowserContext`, which remains Chromium's security object. Creation/shutdown must become a supported production route without another top-level window. |
| Native page registry | `PageId` association with native TabModel/TabHandle and current WebContents, Profile identity and operation generation | Native objects keep actual ownership. Registry references must be invalidated on destruction/replacement; pointers, indices, URL and title are not durable IDs. |
| Native event bridge | Tab insertion/removal/replacement, selection, committed main-frame navigation, destruction, close cancellation and Profile shutdown | Reports observed outcomes on the browser UI sequence. It must distinguish transfer from deletion and discard replacement from a new page. |
| Session bridge | Workspace metadata and joins to Profile-local native session records | Native session machinery remains the navigation-history authority. Cross-Profile restore assembles one intended host rather than independently spawning a window for every context. |

For the focused proof, select one homogeneous tab model per `(WindowId, actual Profile identity)`, with an attachment projection for Space rows, selected page, keyboard cycling, MRU, menus, close commands, splits and accessibility. Spaces sharing a Profile reuse its context and real services while retaining distinct temporary-page presentation and themes. Ordinary same-Profile Space switching changes the projection and selection without detaching background pages. This is an engineering hypothesis for design A, not a product capacity rule. If the projection cannot preserve native command and selection correctness, revisit the container design before model binding.

Native session IDs are session-local. Allocate non-reused workspace identities through a durable allocator and validated restore mapping; do not reinterpret tab indices, pointer values or native SessionIDs as persistent `PageId`/`SpaceId`/`WindowId`. Preserve exact Profile/OTR identities rather than collapsing them to a display name or original-Profile pointer. Private/guest persistence semantics are not approved here. Context lifetime must outlast all its WebContents and service users. [C1](native-space-source-references.md#c1-desktop-window-and-profile-ownership), [C3](native-space-source-references.md#c3-live-identity-and-handoff)

## Production ownership extraction design

Select design A with retained Profile-bound child chrome, the refactored form of C, for the next proof. The actual top-level widget has a host-owned delegate and frame for its whole lifetime. Extract the Profile-specific BrowserView content/chrome into child views owned by their context; an unchanged BrowserView cannot be reparented or used as a second widget delegate. Inactive child views are not hidden top-level windows. Keep their tab/service observers alive while removing their authority over host input, focus and presentation. Rebuilding every Profile controller on each switch is not the selected mechanism.

The following are proposed production interface contracts, not existing C++ declarations or a facade to implement in this documentation task. They replace the combined ownership assumptions rather than forwarding to a stock hidden Browser. [C5](native-space-source-references.md#c5-production-extraction-edges) pins the additional construction, feature and manager evidence.

| Module and changed source edge | Interface contract for the extraction |
| --- | --- |
| Host lifetime manager, extracted from Browser's window ownership and BrowserManagerService's window bookkeeping | A process-lifetime owner creates and owns the actual host/widget independently of any selected Profile. Creation returns a liveness-aware host identity only after native initialization; failure publishes no usable host. Host close is a coordinated request across all its contexts, not a delete through the currently presented Profile. |
| Profile context manager, separated from `BrowserManagerService::AddBrowser`, `DeleteBrowser` and `Shutdown` | The exact Profile's keyed manager owns homogeneous contexts, their tab models and Profile features. A production create-context operation accepts a live host identity and actual Profile, creates no top-level widget, and returns a context identity only after initialization. Host and context reference each other through invalidatable registrations, not competing unique ownership. Shutdown first makes contexts unavailable to new work, then coordinates their pages and transfers before releasing them. |
| Context interface, extracted from `BrowserWindowInterface`/Browser | Expose immutable real Profile, homogeneous tabs, context-local session ID and Profile services separately from host activation/close/frame operations. Do not implement the old desktop window interface with a changing Profile or several pretend windows pointing at one handle. Migrate each affected consumer to a context, host or presentation target; retain the old invariant for remaining ordinary windows. |
| `BrowserWindowFeatures` initialization and teardown | Split Profile/tab features from host/widget features and presentation bindings. Context features initialize once with the immutable context; host features initialize once with the real widget; attach/detach operations bind retained child chrome without rerunning once-only `Init*` on a new Profile. Preserve dependency order and reverse teardown, including unload, bookmark, command, session, sign-in, exclusive-access and DevTools dependencies. Every enabled member needs an owner classification before the proof is accepted. |
| BrowserView/BrowserWidget and child chrome | Host owns the widget delegate, frame, layout and native destruction callback. Context owns toolbar/location-bar/controller state and child contents views. Attaching child chrome must return a prepared presentation binding; activating it grants input authority. Detaching it revokes that authority without destroying pages or changing their BrowserContext. Native-widget destruction no longer selects one Browser through `browser_view_->browser()` for synchronous deletion. |
| Profile and process keepalives | Host lifetime holds application liveness even when its selected context is empty. Context lifetime retains the exact Profile and its required keyed services through all pages, child chrome and transfer reservations. Move/split the existing Browser process keepalive responsibility explicitly and preserve shutdown ordering. The regular-Profile keepalive in Browser and special OTR destruction in the manager are distinct paths; regular-Profile proof does not approve private/guest persistence. |
| Native-window lookup and collections | Native handle resolves to the host. A separate lookup returns an optional presented-context/Space/page binding with an operation generation. Context-to-host lookup does not imply visibility. Replace consumers of `kBrowserViewKey`, `Profile::kProfileKey`, Aura theme routing and browser collections according to their actual need. A Profile lookup is not an authentication authority. Host activation/window counts are distinct from context creation/presentation events. Never register inactive contexts as extra OS windows. |
| Command and callback dispatch | Host window commands receive the host identity. Profile actions receive the explicit context/Profile. Page actions receive the presented page and its actual context. One activation binding owns host accelerators, macOS menu targets, focus and accessibility links. Queued work carries its originating context/page/generation, never retargets itself through current selection, and checks liveness before presentation. Service observations for inactive pages continue. |
| Profile-local session registration | Register each context's homogeneous tab/session records with its own Profile service, and join `(host, Profile, native session ID)` to durable workspace identities separately. `WindowOpened`/`WindowClosed`, SessionTabHelper window IDs, selected indices, window geometry and platform session data need separate context-record and physical-host meanings. One host close closes all relevant context records once; switching Spaces closes none. Restore must assemble contexts under one intended host, not invoke stock window creation per record. |

Creation order is host lifetime reservation, exact-Profile context/keepalive reservation, context tab/features initialization, child-chrome construction, presentation binding and host-ready publication. Source-backed dependencies may require a staged host shell before child views are constructed; that shell must already be the intended actual widget, never a replacement/backing window. No construction callback may expose partially initialized command targets. The asynchronous creation convention in C1/C5 still requires liveness revalidation on callback.

For a switch, prepare the target context, attachment projection, child chrome and Space theme before revoking the old activation binding. Commit the visible child tree, command target, native lookup binding, focus/accessibility and theme as one coordinated UI-sequence transition, then publish semantic selection. Synchronous observers and queued callbacks must not see a mixed Profile/chrome target. On preparation failure keep the old binding; on presentation failure restore it before reporting failure. A pending modal, permission, fullscreen or capture owner must remain bound to its source context. Defer/fail the switch if it cannot be safely retained or reanchored; never dismiss protected work merely to make switching succeed. The native proof must establish this ordering; the table does not supply atomicity.

Space theme presentation is a host presentation input keyed by `SpaceId`, distinct from Profile services. The selected Space supplies a theme overlay to the frame and attached chrome's color/theme resolution. Invalidate the widget and child color providers on Space/theme change, including a same-Profile switch. Preserve native accessibility, system contrast and security indicators. Profile ThemeService may provide a base, but changing the Space theme must not write Profile theme preferences or mutate a shared supplier affecting another Space/window. BrowserWidget's current Profile-based theme/provider path therefore needs extraction even when the context does not change. [C2](native-space-source-references.md#c2-view-widget-and-command-coupling)

### Empty contexts and teardown

`TabStripEmpty` becomes a context-state notification, not `window_->Close()`. Keep the empty context and its registration alive until coordinated host close or Profile shutdown. An empty selected attachment shows native empty chrome with the selected Space's theme and correct Profile target, with page-only commands disabled. Other attachments may still have pages in that same context; its internally active tab must not leak into the empty Space. New Tab targets that empty attachment and real Profile. No dummy WebContents or cleanup policy is introduced.

An empty context must not close its host, another Profile's context or a source host emptied by handoff. If all contexts are empty, the host still remains until an explicit native close request. This separates window lifetime from tab count as required by the host design; it does not approve destructive tab/window-close policy. Before a context is released, revoke input/presentation, invalidate outstanding bindings, finish or retain ownership of detached pages, drain source-owned callbacks safely, tear down features/chrome in dependency order, and destroy WebContents before Profile release. Remove registry and session registrations exactly once. Keep close subscriptions alive through owner destruction as the pinned manager does. Host/widget release follows coordinated context teardown; Profile-service shutdown cannot blindly destroy the shared host. Outstanding work or a cancelled close leaves the affected owner live and reports failure instead of claiming teardown completed.

Unexpected native-widget destruction follows a separate failure path: invalidate host lookup and presentation bindings immediately, stop dispatch to that widget, and notify the coordinator while Profile managers retain context/page ownership for reconciliation. Never run the legacy synchronous deletion against whichever Profile was selected. Recovery from a lost native surface remains a native proof obligation; retaining a context does not claim that its vanished host or presentation survived, and does not authorize creating a hidden replacement.

## Commands and native completion

Route pointer and keyboard actions through the same native command path. Space commands target stable host/Space IDs. Page commands target a stable page and its immutable Profile. Profile commands receive an explicit Profile target. Window commands target the native host. Preserve native URL policy, origin/opener handling, before-unload, modal-dialog and discard rules. Do not turn the lifecycle model into a parallel navigation engine. [C2](native-space-source-references.md#c2-view-widget-and-command-coupling), [C4](native-space-source-references.md#c4-navigation-and-session-boundaries)

For switching, resolve the attached Space and real Profile, prepare the corresponding browsing context, deactivate old context-specific accelerators/observers/chrome, and present the target context in the existing host. Confirm that selected content, omnibox, services, native properties, focus and accessibility agree before publishing selection. If preparation or presentation fails, retain the prior selection. Empty Spaces require a real empty presentation, not a dummy navigation or another window. The model's `SelectSpace` alone cannot acknowledge this operation.

For a saved item already live elsewhere, keep its Profile unchanged even if the requesting host currently presents another Profile. Resolve the item's destination attachment under the contract, prepare the matching Profile-bound context in that host, and transfer the existing page there. A kept item's owning Space remains its destination; an alias requires that owning Space to be attached. Opening the item and switching to its resolved Space are separate semantic operations that the UI coordinates explicitly.

1. Snapshot owned command IDs, current attachment, native handles, resolved destination and operation generation. Serialize conflicting page/host operations and revalidate native liveness, Profile compatibility and attachment permissions before detachment. V3's mutating commands have no native prepare/commit interface. Design that boundary before wiring commands; do not call `OpenItem` speculatively and pretend its model mutation completed native work. Its pure link planner does not add a transfer transaction.
2. Use the native TabModel-preserving detach/insert path as the candidate mechanism. Retain exclusive ownership of the detached object across the gap. `DetachWebContentsAtForInsertion` destroys the wrapper and loses its features; it is a different operation. Do not clone, serialize, reload, discard or create a replacement page for a successful live handoff. [C3](native-space-source-references.md#c3-live-identity-and-handoff)
3. Account for synchronous observers, delegate removal/rebinding, source split cleanup, cleared opener/blocked bookkeeping, modal ownership and empty-strip callbacks. Moving the last tab must not destroy the source host or its other Profile contexts. The existing close-window flag adds a tab on close paths; it is not a transfer solution. A safe route for active modal/capture UI is an implementation gate, not an assumption that the page is quiescent.
4. Confirm destination ownership and presentation, then commit semantic transfer and selection with the same `PageId`. Prune old split references as the historical v2 behavior, retained in v3, requires; do not transfer a split layout or invent a target split. Publish the resulting sidebar state to affected windows. A same-attachment selection must retain layouts.
5. On cancellation, stale destination or insertion/presentation failure, retain or reattach the exact object to a still-live source. Keep the transfer owner alive while resolving callbacks. If source closure races with failure, hold ownership and resolve the close through the same coordinator; do not destroy protected work, fabricate rollback success or mark the operation committed. No atomic native transaction is supplied by these APIs. The deferred native proof must establish a recovery path before this feature ships.

Temporary pages never enter this transfer command. Protected/unknown saved-page activity is retained during transfer; it is not a close/reset approval. Activity detection, manual-close review and cleanup remain governed by the unresolved contract choices.

Native insertion/removal events during an in-flight operation reconcile its registry and transaction; they must not independently create another page or report a close. A late navigation event remains associated with its originating page/context, not the currently selected Space. A native discard may replace WebContents while retaining the logical page, so the registry must observe replacement; this does not authorize discarding during handoff. Renderer crash, Profile shutdown and native close cancellation each need explicit reconciliation. Generation tokens prevent stale completion from selecting a different page; they are not retry counts or timeouts.

### Approved outbound-link integration

Adopt v3 `PlanSavedPageLink` only for a browser-proven link trigger and authoritative outbound classification relative to the source's current committed document. The native navigation seam must supply URL validation, document identity, initiating origin, referrer, opener relationship, user gesture and security policy through Chromium's real navigation path. Do not infer outbound from URL text or treat a changed Profile property as navigation authority. [C4](native-space-source-references.md#c4-navigation-and-session-boundaries)

Resolve the source page's current attachment, not the host's possibly newer selected Space. The branch is a fresh local temporary page in that attachment under the source's immutable actual Profile. It is not an additional saved-page instance or a transfer. Keep the source TabModel/WebContents/controller/document, saved destination, current navigation, activity and split references unchanged. Native opener/security processing may legitimately constrain or clear an opener; never fabricate an opener across Profiles to satisfy a semantic snapshot.

The planner returns an owned snapshot, with no reservation, IDs or native actuation. Revalidate source/document/Profile/attachment and native classification before creating the temporary, reserve model preconditions under the coordinator, and report actual native success through `OpenTemporary` with fresh IDs and the actual destination. Failed/cancelled creation records no branch. If native success races with reporting failure, retain and reconcile the real temporary owner; never silently orphan it or destroy the protected saved original. A redirect is not a new approved link and cannot reuse the plan as routing authorization. Same-site/unknown classification and redirects/scripts/typed/other triggers stay outside this approval without choosing a browser-wide block or an in-place fallback. Cleanup, reset and destructive close policy remain **OPEN**.

## Persistence and restoration

Keep saved destinations and workspace organization in a versioned, graph-validated durable record. Add explicit Space order and presentation selection records alongside the v3 standalone model; decide the selected-page scope consistently with the lifecycle contract before implementing restore. Do not infer that a map's key order is user order. Do not store another copy of current navigation or live form state as workspace metadata.

Retain native Profile-local session storage for navigation entries and pending-load restoration. Add stable workspace-to-native-session associations and host grouping, with a defined commit/recovery protocol for transfer across those records. The protocol must tolerate an interrupted write without duplicating a saved live page or silently losing the selected Space. Neither historical semantic version 2 nor adopted version 3 is an on-disk format. SessionService's Profile checks and tab/window association cannot be bypassed to place mixed-Profile records in one Profile's session. [C4](native-space-source-references.md#c4-navigation-and-session-boundaries)

Restore Profile contexts into the intended native host through the new production ownership route, reconcile workspace identities against actual restored tabs, then publish order and selection. Reuse Helium's selected-first lazy restore and split reconstruction, including skipped navigation entries. Do not mark every inactive Space visible/active and eagerly load it to simulate preservation. Crash/restart restoration has different guarantees from an ordinary switch or transfer of a running renderer; do not promise recovery of live forms or server effects from metadata.
